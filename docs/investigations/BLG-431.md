## Step 1 — SessionRail's 1 Hz ticker (DONE, commits `7e80c76c`, `35966e58`)

`runner/frontend/src/components/SessionRail.tsx` is one ~1,400-line function
component. Its top called `useTicker(timed)` (`@blerglab/chat`'s plain
`setInterval(…, 1000)` + `setState`) whenever anything was "timed" (Main
working, a subagent, an open ask, a background task, or a running child).
Because that state lived in `SessionRail` itself, every tick re-ran the
*entire* component body — Needs-you, Tickets, Checklist/Plan, Diffs,
Workspace settings, none of which show a clock — on top of the rows that
legitimately advance (`MainRow`, `SubagentRow`, `TaskRow`, `AskRow`,
`ChildSessionRow`, none of which were memoized either, so *any* SessionRail
re-render, ticker or not, re-ran all of them). A separate local `useMinute`
(30 s) did the same for `SessionFacts`'s lifetime label.

This matches BLG-362's lead precisely: the existing perf test
(`LongSession.performance.browser.test.tsx`) holds every timer registered
before the measured keystroke and only lets one through at the exact moment
of the synthetic keystroke, so it cannot see what happens when the ticker
fires on its own schedule and lands in the same frame as a real keystroke —
a single self-contained ~1,400-line re-render large enough to delay whatever
keystroke is queued right behind it on the same JS main thread.

**Fix:** moved each clock into the row that actually shows elapsed time
instead of computing it once at `SessionRail`'s top and threading it down as
a prop:
- `AskRow`, `SubagentRow`, `TaskRow`: take `clockOffset`/`active`, self-tick
  via `useTicker`, wrapped in `React.memo`.
- `MainRow`: takes `sessionId`/`active`, self-ticks and runs `useMainStep`
  internally. Its *presence* (needed for Running-now's badge count, with no
  clock) turned out not to need `now` at all: `useMainStep(id, now)` is
  non-null exactly when the working-line store has a line for this session,
  regardless of what `now` is — only the *text inside* the step depends on
  the clock.
- `ChildSessionRow`/`RunningChildRow` (`ChildSessions.tsx`): same treatment,
  renamed the clock-active flag to `ticking` (the row already has a local
  `active` meaning "is this child actively running").
- `SessionFacts`: self-ticks its own 30 s clock instead of reading one
  computed at `SessionRail`'s top.

**Regression test:** mounts `SessionRail` directly (not through
`SessionDetail`/`useLiveStateServer`, which has its own real ~5 s rate-
limited re-read of `/live`, unrelated to this ticker and not yet isolated —
see Step 2) with a running subagent and task, lets every real timer run for
3 real wall-clock seconds with nothing held, and counts React Profiler
commits. `SessionRail`, `RailBody`, `HistoryTab`, `ChecklistRow`,
`TicketCard` stay at 0; `SubagentRow`/`TaskRow` each tick at least once.
Confirmed red: temporarily reintroduced the removed top-level
`useTicker(true)` call, watched `SessionRail` go from 0 to 1, reverted.

**Verified:** `tsc -b` clean. `npx vitest run` on the touched files plus the
full `LongSession.performance.browser.test.tsx` suite: 269/32 passed (two
separate full runs), 0 failed, 4 skipped, load average ~8-13 throughout —
the suite's own wall-clock budget assertions passed unchanged, not just the
new render-count one.

## Step 2 — useLiveStateServer's staleness clock (DONE, commit `0c54ea34`)

`useLiveStateServer.ts`'s internal `useMinute()` ticked every 60 s
*unconditionally* — no `enabled` gate, no visibility check — re-rendering
whatever calls it (`useSessionLive`, from `SessionDetail`: the whole session
page) that often, for every open agent-session tab, even hidden ones. Its
only consumer is `foldLive`'s 12 h stale-running cutoff (`STALE_RUNNING_MS`)
and an MCP tool-change hold's own expiry — neither needs minute resolution.

Unlike Step 1, this isn't a component-split fix: the value this clock feeds
(`foldLive`'s fold) is load-bearing for the whole hook's return value, not
an isolable display leaf, so the correct "same treatment" here is cutting
frequency and gating by visibility, not splitting a component.

**Fix:** ticks every 15 minutes, only while the tab is visible (checked on
the interval and via a `visibilitychange` listener, so a hidden tab catches
up the instant it becomes visible again, or on any real event/read via the
hook's existing triggers in the meantime).

**Regression test** (`useLiveStateServer.test.ts`, fake timers): counts
render calls; proves 14 min visible-or-hidden → 0, 15 min visible → exactly
1, an hour hidden → 0, becoming visible again → catches up at once.
Confirmed red (reverted to the unconditional 60 s interval, watched the test
fail expecting 2 renders and getting 3, restored the fix).

**Verified:** `tsc -b` clean. `useLiveStateServer` (16/16), every other test
file touching `useSessionLive`/`useLiveStateServer` (`ChildQuestions`,
`SessionBoardParity`, `SessionBoardTabs`, `useSessionLive.answers` — 59/59),
and the full `LongSession.performance.browser.test.tsx` suite (32/32).

## Step 3 — workspace switch (PARTIAL, commit `b6f3e14a`)

**Measured** (`SessionSwitch.performance.browser.test.tsx`'s existing
`budgets switching into a long live workspace with three panels`, load
average ~9-10): median **1061.9 ms**, matching the owner's own earlier

**Not yet checked:** the snapshot store (`lib/snapshots.ts`, BLG-449/451) —

an in-memory client cache rather than a per-switch network cost; more
likely a memory-growth question (keeps every chart/diagram a tab has

**Not done:** a *new*, tighter switch budget test exercising the full

## Step 4 — CPU-throttled real-clock gate tests (built; HELD by the owner pending recalibration)

Added `commands.setCpuThrottling(rate)` (`src/test/cpuThrottle.ts`,
registered in `vitest.config.ts`): a real Chrome DevTools Protocol
`Emulation.setCPUThrottlingRate` call (not a software shim), reusing the
same `context.newCDPSession(page)` pattern `workspaceTrace` already uses in
`transcriptInput.ts`. Two new gate tests use it with every real clock
running (no `manageTimers` hold):
`LongSession.performance.browser.test.tsx`'s `keeps typing under budget at
4x CPU throttle, with every real clock running`, and
`SessionSwitch.performance.browser.test.tsx`'s `keeps a workspace switch
under budget at 4x CPU throttle`.

**A real, load-bearing finding from building this:** a flat 20M-iteration
JS loop under `rate=4` with no React/DOM involved took **50 s** in this
sandbox — a >1000x slowdown, not a clean 4x one. Repeated runs of the real
typing-budget test showed the *same keystroke* measuring 5.9 ms one run and
1732.8 ms another, and the CDP throttle-apply call itself (the one line of
code, not the test's own work) took anywhere from 33 s to 180+ s to
acknowledge across runs, sometimes not completing inside a 280-300 s bound
at all. Checking `ps` while this was happening found the contention's real
source: other sessions' own `vitest run` processes (confirmed via `ps`,
e.g. a concurrent run from `/tmp/blg-452-chart-renderer`) genuinely
competing for the same host's CPU — exactly the "gate plus workers, six
headless browsers" state the owner named at the start of this session, not
a bug in the throttle command or the code under test.

Given that, the two tests' budgets (3000 ms for one throttled keystroke,
10000 ms for one throttled switch) are deliberately generous placeholders
sized to survive this specific sandbox's observed worst-case noise while
still catching an actual regression (reverting Step 1's SessionRail fix
measured in the seconds under 4x here, not low hundreds of ms) — they are
**not yet tuned against a quiet, dedicated gate runner**, because this
sandbox cannot currently provide one. Recommend running these a handful of
times on the actual CI/gate machine once merged, watching for flakiness,
and tightening the threshold from the real numbers that machine reports
rather than this session's.

## Fix: board tab first paint (owner's follow-up, 2026-11-03)

The owner's instruction assumed the 3710.7 ms/3879.9 ms board/Insights
numbers were the board's and Insights's own cost. Digging in to fix it
found otherwise, and the fix had to change shape once that was clear.

**What the original measurement actually measured.** It mounted the whole
`longWorkspace` fixture cold (50,000 transcript events, 5,000 retained
sessions, 400 board cards, subagents, tasks, all at once) and timed to
"Task 400" (the board's last card) from that mount. Two signs this wasn't
the board's own cost: a *standalone* `SessionBoardTabs` render with the
same 400 cards, measured directly (no SessionDetail around it), took
**180.8 ms** end to end - nowhere near 3.7 s. And in the original
measurement, `boardMs` (2751 ms) and `insightsMs` (2789 ms, cumulative
from the same start) were nearly identical - if either tab's own work were
the cost, the second number would be meaningfully larger than the first.
Both tabs' numbers were dominated by something shared: mounting the rest
of a 50,000-event session for the first time, which is not what "board tab
first paint" or "Insights tab first paint" are about.

**Fix shipped anyway, for a different reason.** `SessionBoardTabs.tsx` had
no windowing at all - every card in a column mounted in one commit,
unconditionally. Added `useProgressiveReveal`: on a genuinely cold load (no
cached page in memory), reveals 60 more cards every animation frame until
all are mounted; a cached revisit or a background refresh shows everything
at once (no artificial delay when there is nothing to hide a wait behind).
This is real, defensible protection against a much larger board (the
fixture's 400 in one column is not representative of every board) even
though it is not what explains the 3.7 s number - see below. The existing
`cachedBoardPage`/`rememberBoardPage` cache this ticket's lead also asked
for ("reuse the board cache on a revisit") already existed before this
pass; confirmed, not re-implemented.

**Rewrote the measurement to match what a person actually waits on**:
opening the board tab (via its real "Open board: <name>" button) and the
Insights tab (via its real "Insights" button) from an *already-mounted*,
otherwise-idle session - not a cold mount of the whole heavy fixture. This
is the real "tab first paint" question; the previous test's number was a
different, legitimate-but-differently-named thing ("cold full-page mount
with these two tabs present").

**Before/after, same corrected test, with and without windowing (load
average ~8-9 throughout; see the owner's 2026-11-03 instruction to measure
under 8)**:

- Board tab open, first card visible: before 306.8 ms, after 286.7-288.1 ms
  (two runs). Fully revealed (every card): before 322.3 ms, after
  297-303.8 ms. Windowing's effect here is real but small (~20 ms) because
  400 simple cards in one column were never expensive to mount - the
  2026-11-02 target's premise (400 cards causing the slowness) does not
  hold for this fixture.
- Insights tab open: 141.4-219.6 ms across runs (not affected by the board
  change at all - a separate tab, reported for completeness).

Both are already comfortably under the 1 s target once measured correctly;
neither needed the 3.7x/3.9x reduction the original framing implied, because
the thing that actually took 3.7-3.9 s was never the tab's own open cost.
Left unexplored: what specifically in a cold `longWorkspace` mount (50,000
transcript events is the prime suspect, not measured in isolation this
pass) costs ~3.5-3.7 s, since that is a real number too, just not an answer
to "how long does opening the board/Insights tab take."

## Fix: GET /live at 255 ms (owner's follow-up, 2026-11-03)

**EXPLAIN first.** Ran `EXPLAIN (ANALYZE, BUFFERS)` against the exact
`LiveEventsSQL` query (`ListLiveEvents`'s main read) on a seeded
100k-event session: 11.85 ms, using `agent_events_live_idx` (a partial
index from migration 042) via a bitmap index scan - not slow, and not the
cause. So the 255 ms is not one slow query.

**pprof-equivalent by counting, not profiling**: `snapshotHandleGetLive`
makes roughly 15-20 *sequential* round trips to Postgres - GetSession,
MaxAgentEventSeq, CountPendingToolChangesForSession,
CountPendingProposalsForSession, ReadAskRows, livePendingReviews,
readChildrenSnapshot, liveChildAsks, conditionally ListOpenAsks/
ListModelPrices/OpenMembershipOperation, sessionRepo, pendingAnswerViews,
ListLiveEvents (2 queries), buildLiveState's subagent-tail queries,
readWorkState, liveChildren, conditionally sessionLiveUsage,
addChecklistCommitURLs - each individually fast, but none of them
depending on each other's *result* (only on sid/account/row, already in
hand), so their round-trip latencies summed instead of overlapping. The
ETag itself needs almost all of them before it can even answer a 304, so
none of this is skippable on an unchanged read.

**First attempt (reverted): goroutines.** Ran the ~10 independent reads
concurrently via `errgroup`. Measured *worse*: 348.9 ms and 359.9 ms
across two runs, against a 255.3 ms sequential baseline. Root cause: the
test database pool here is `MaxConns = 2` (`testsupport/database.go`);
10 goroutines contending over 2 connections pay checkout/scheduling
overhead with no real parallelism gained. More importantly, this is not
only a test artifact - `runtime_fence.go` explicitly supports installs
configured with `MaxConns = 1` ("including installations configured with
MaxConns=1"), where goroutine-level concurrency across connections cannot
help at all, by design. Reverted; a concurrency fix is wrong for this
product's supported range of installs.

**Shipped instead: fewer round trips, not more concurrency.** Added
`db.LiveCounts` (`internal/db/reel.go`): one query combining three of the
independent scalar reads - the newest seq, pending tool changes, pending
proposals - each as a subquery, replacing three separate round trips with
one. This helps regardless of `MaxConns`, including the 1-connection
case, because it is fewer round trips over whichever connection is used,
not more connections in flight. The other ~7 independent reads return
structured rows rather than scalars and were not combined this pass - see
Open work.

**Before/after**, measured in pairs (baseline, then fix, run immediately
after each other to control for this test database's own run-to-run
variance, which was substantial this session - 250-360 ms observed for
the *unmodified* code across different moments):

| pair | baseline | fix |
|---|---|---|
| 1 | 340.2 ms | 255.4 ms |
| 2 | 350.7 ms | 252.4 ms |
| 3 | 358.5 ms | 247.9 ms |

Consistent ~90-110 ms reduction (~27-30%) across all three pairs, run
back-to-back each time specifically because a single baseline-then-fix
comparison (not paired closely in time) would have been misleading here -
the environment's own noise (250-360 ms for identical unmodified code)
is larger than naive single-sample before/after deltas.

Verified: `go build ./internal/db/... ./internal/server/...` clean,
`gofmt` clean. Ran only the touched tests: `TestGetLiveAccessMatchesTheReel`,
`TestGetLiveReadsTheWholeLog`, `TestGetLiveETag`, `TestGetLiveOnALongSession`
(4/4 passed, each run). No other caller of `MaxAgentEventSeq`/
`CountPendingToolChangesForSession`/`CountPendingProposalsForSession` was
touched - they stay in place, used elsewhere; `LiveCounts` is new, used
only from this one call site.

## Server/daemon (slowest routes, polling load, memory growth)

**Slowest API routes.** Two routes already have their own perf-gated Go
tests seeding a 100k-event session (`livestate_test.go`'s
`TestGetLiveOnALongSession`, `topics_test.go`'s
`TestGetTopicsOnALongSession`), normally asserting a loose 2 s bar but
opting into a strict one via `BLERG_PERF_ASSERT=1`. Ran both once (real
test database, `go test ./internal/server/ -run
"TestGetLiveOnALongSession|TestGetTopicsOnALongSession"`):

- `GET /live` on 100k events: best of 3 = **255.3 ms** — over its own
  200 ms strict bar (which is not enforced by default; this is a real
  measurement, not a new failure I introduced). This is the single most
  relevant number here: `/live` is the route `useLiveStateServer` polls
  (Step 2), rate-limited to once every 5 s per session but re-triggered by
  real events, so it is the route every open agent-session tab actually
  hits.
- `GET /topics` on the same 100k-event session: **137.4 ms**, within its
  own bar.

No other route has this kind of seeded-long-session perf test; did not add
new ones this pass given the instruction to keep test runs to what each
change touches.

**Polling load from open tabs.** Compiled from what steps 1-3 already
catalogued, per session tab actually open (not hidden/backgrounded unless
noted):

- `useLiveStateServer`: up to 1 read of `/live` every 5 s (`LIVE_MIN_GAP_MS`),
  only while something is actually happening (a real transcript trigger),
  not a blind interval — N open tabs each receiving events is up to N
  reads every 5 s, i.e. up to 0.2 N req/s to the daemon.
- `cardTimeData.ts`: 1 read per *distinct pinned-card/checklist-item
  reference* every 60 s it is stale, shared across every tab via the
  module-level cache (not per-tab) — a person with many tabs open on the
  same few cards costs the same as one tab.
- `BlackboardTabs.tsx`'s open `BlackboardScreen`: 1 read every 30 s per
  open blackboard tab.
- `BlackboardButton` (fixed this pass): was 1 read per mount/switch with no
  cache; now shares the same 60 s window as card-time, so repeated
  switching no longer multiplies this one.
- Several 15 s polls gated on `document.visibilityState === 'visible'`
  already (`ClusterStatus`, `UsageLimitResume`, `SessionPermissions`,
  `DockRepositories` membership) — correctly scoped, not re-checked here.

Order of magnitude: a person with, say, 10 open agent-session tabs, several
actively working, is plausibly a handful of `/live` reads per second at
peak, each costing up to ~255 ms server-side on a long session per the
number above — close enough to the 5 s gap that two or three busy tabs
could occasionally queue behind each other, though `useLiveStateServer`
only runs one read at a time per session (not globally), so tabs don't
block each other's reads.

**Memory growth.** Checked for unbounded client-side caches (the shape of
growth that would show up over a long day, not a quick leak): `useLiveStateServer.ts`'s
own per-session `Held` map is already bounded (`KEEP = 20`, evicts the
oldest). `cardTimeData.ts`'s `reads`/`inflight` maps have **no such
bound** — every distinct (account, board, card) visited in a session's
lifetime stays in memory until an identity change clears it; on a given
account this is realistically bounded by how many actual cards exist, so
low risk, but worth noting as the one unbounded cache found. My own new
`BlackboardButton` cache (this pass) had the same gap; capped it to
`KEEP = 20` (same pattern as `useLiveStateServer.ts`) before it shipped
rather than filing it as a finding to fix later.

Checked `lib/snapshots.ts` (BLG-449/451's chart/diagram/message snapshot
store, the lead this ticket named): it is **already explicitly bounded**
— `PER_SNAPSHOT_CAP` (1 MB) per entry, `PER_ACCOUNT_CAP` (8 MB) total,
oldest-first eviction excluding anything still referenced by an open tab
layout (`protect`). Not an open memory-growth risk; this lead is resolved
as "already handled," not deferred.

Server-side (Go) memory growth over a long-running day was not measured —
that needs a long-lived process with heap snapshots over real wall-clock
time, which the "run only the tests each change touches" instruction and
this sandbox's own constraints make impractical to do well in this pass;
flagged as open work below rather than attempted shallowly.
